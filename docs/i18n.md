# Output languages

No renderer writes a user-visible word itself. Every heading, label, calendar name and condition
text is a Fluent message: the renderer asks `src/i18n.rs` for a **key**, and the key is what a
catalog is written against. The catalogs are Fluent files under `locales/`, embedded in the binary
with `include_str!` — there is no runtime catalog directory to find, and a missing translation is a
failing test, not a silent English string in the middle of Chinese output.

This file owns the language set, selection and the add-a-language recipe. The `defaults.language`
key's type and built-in default live in [configuration](configuration.md); the `%`-token table that
decides which of these messages a `one-line` template reaches is in [formats](formats.md); the JSON
keys that are deliberately *not* translated are in [schema](schema.md).

## Shipped catalogs

The source of truth is `CATALOGS` in `src/i18n.rs`:

```rust
pub const CATALOGS: &[(&str, &str)] = &[
    ("en-US", include_str!("../locales/en-US/main.ftl")),
    ("zh-CN", include_str!("../locales/zh-CN/main.ftl")),
];
```

| Tag | File | Role |
|---|---|---|
| `en-US` | `locales/en-US/main.ftl` | the built-in language (`DEFAULT_TAG`) and the fallback resource of every chain; its catalog must be complete |
| `zh-CN` | `locales/zh-CN/main.ftl` | Simplified Chinese |

Every catalog carries exactly the English key set — the completeness test rejects both a missing
key and an orphan key the English catalog does not have. The `available:` list in a language warning
is built from these tags.

## Selecting a language

Highest priority wins, exactly as the `CONFIG PRECEDENCE` epilogue of `--help` states:

```text
--lang > CIRROCAST_LANG > defaults.language > built-in default
```

`--lang` (and its `CIRROCAST_LANG` variable) takes an output language as a BCP-47 tag, or `auto`:

```text
      --lang <TAG>
          Output language as a BCP-47 tag, or `auto`

          [env: CIRROCAST_LANG=]
```

The built-in default of `defaults.language` is `auto`, so a run with nothing configured negotiates
from the ambient locale. `config get defaults.language` prints the file value; when the environment
variable is set, the variable's value is what the command prints.

### `auto` negotiation

`auto` (and `C`/`POSIX`) reads the ambient locale through a fixed POSIX order:

1. `LC_ALL`
2. `LC_MESSAGES`
3. `LANG`

Each value is normalised before comparison: everything after the first `.` (the codeset) and `@`
(the modifier, as in `sr_RS@latin`) is dropped, `_` becomes `-`, so `zh_CN.UTF-8` is the tag
`zh-CN`. An empty value, `C` and `POSIX` mean "no locale" and are skipped, which is what the
`LC_ALL=` idiom relies on. A variable that names a language this build has no catalog for does not
stop the walk — `LANG=de_DE.UTF-8` still leaves `LC_MESSAGES` free to name `zh_CN` — and the first
variable that resolves wins. If nothing does, the language is `en-US`.

The **fallback chain** is an explicit map down to `en-US`, not a generic language-prefix match: a
region-less `zh` and a Traditional `zh-TW`/`zh-HK` both land on `zh-CN`, `en-*` lands on `en-US`,
everything else lands on `en-US`. Identifiers this build cannot answer with stay in the chain so the
`-v` line shows what was skipped rather than silently shortening it.

That substitution is documented, so it is *not* a warning: an `en`/`zh` family request resolves
through the chain silently. A request the build cannot serve at all — `de-DE`, `fr-CA`, `bad-TAG` —
falls back to `en-US` and warns:

```text
warning: unsupported language "de-DE", falling back to en-US (available: en-US, zh-CN)
```

A language is never a usage error: the forecast is still what the user asked for, so the run falls
back and continues. `-q` suppresses the warning.

### Examples

| Request | Selected | Warning |
|---|---|---|
| `zh-CN` | `zh-CN` | — |
| `zh-TW`, `zh-HK`, `zh` | `zh-CN` | — |
| `en`, `en-GB`, `EN` | `en-US` | — |
| `de-DE`, `fr-CA`, `bad-TAG`, `!!` | `en-US` | yes |
| ambient `LANG=zh_CN.UTF-8` | `zh-CN` | — |
| ambient `LANG=de_DE.UTF-8` | `en-US` | — (ambient locales walk on) |

### Reporting the choice

`-v` prints the settings line and, after the layout, the resolution line. A substitution is shown
from the user's own spelling:

```text
language: zh-TW (from the command line)
i18n: requested zh-TW → selected zh-CN (chain zh-TW → zh-CN → en-US)
```

An ambient locale echoes the spelling that decided, and a run that got exactly what it asked for
names only the language:

```text
i18n: requested zh_CN.UTF-8 → selected zh-CN (chain zh-CN → en-US)
i18n: en-US (chain en-US)
```

## What is translated

The catalog keys cover everything a renderer puts in front of a reader:

* **Condition text** — the WMO 4677 name of `%C`, the `plain` and `json` condition text, and the
  `art-table` day-part lines. The model describes codes 0..=99; every undescribed code shares
  `cond-unknown`, so a code this build cannot name is still a word, not a raw number.
* **Calendar and layout labels** — report/record labels (`label-report`, `label-*`), the four day
  parts, seven weekday names, twelve month names, and the three date styles assembled from them.
* **Values the renderers name** — UV bands, the sixteen compass points, moon phases, alert
  severity/urgency/certainty and source names, the alert banner fragments and credits, AQI panel
  titles, categories, pollutants and pollen species, marine and climate-normal labels.
* **Measurement spellings** — the `format-*` messages. The number is converted and rounded by
  `src/model/units.rs`; only the symbol and its spacing come from the catalog (`22°C` could be
  `22 ℃`). The unit table is `en-US` by design: weather is written in metric symbols in every
  shipped locale.

## What is not translated

* **JSON keys.** `--format json` carries translated *values* (the condition text) under stable
  English keys; see [schema](schema.md) for the document contract.
* **Provider identifiers and names.** `provider list` / `provider info` and the provider ids are
  the registry's, not the catalog's.
* **The CLI itself.** `--help`, usage and error messages are English; the man page is generated
  from the clap definitions and is English for the same reason.
* **The `plain` record-key shape.** A `label-*` translation may change the word before the colon
  but not the line's shape: lower case and `key: value` are the format contract, not styling.
* **Charset-dependent glyphs.** The `art-table` condition glyph and the wind arrow follow the
  terminal's charset, not the language, so `dumb` output gets a different glyph than a UTF-8 one
  with the same catalog.

## Adding a language

`AGENTS.md` states the recipe; it is exactly this:

> **Add a language**: drop `locales/<tag>/main.ftl` (copy `en-US`), translate every key, add the
> `("<tag>", include_str!("../locales/<tag>/main.ftl"))` line to `CATALOGS` in `src/i18n.rs` (the
> `include_str!` embedding is what requires that one line), run `cargo test i18n` — the completeness
> test fails if any condition key, renderer key or `en-US` key is missing. Nothing else changes.

In full:

1. Copy `locales/en-US/main.ftl` to `locales/<tag>/main.ftl` and keep its `#` SPDX header.
2. Translate every value, keys unchanged. Do **not** add, drop or rename a key: an orphan key fails
   the same test a missing one does (the English catalog is the reference set).
3. Add one line to `CATALOGS` in `src/i18n.rs`:
   `("<tag>", include_str!("../locales/<tag>/main.ftl")),`.
4. Run `cargo test i18n`.

The `include_str!` is why the code change is required: the catalog is compiled into the binary, so
a new file is invisible until it is named. There is no build script and no renderer change, and no
catalog is read from disk at runtime.

## The completeness test

`tests/i18n.rs` checks every catalog twice, because a catalog can fail in two ways.

| Test | What it pins |
|---|---|
| `every_catalog_carries_every_key_the_renderers_ask_for` | each catalog's key set is set-equal to `en-US` (no missing, no unknown keys), and contains every renderer key |
| `every_catalog_resolves_every_key_through_the_bundle` | each catalog loads through the public path and resolves every renderer key with the full argument set; a key that renders back, renders empty, or leaves `{`/`}` fails |
| `the_renderer_key_list_carries_every_direction` | the sixteen `dir-*` keys stay in `RENDERER_KEYS` |
| `an_unknown_condition_has_a_name_of_its_own` | undescribed codes resolve to `cond-unknown`, a described code keeps its name |
| `a_pattern_error_returns_the_raw_key_not_a_half_render` | a message missing an argument yields the raw key and a `MissingKey` note, never `{$value}` |
| `every_catalog_parses_and_carries_the_same_keys` (unit test) | `en-US` spells out `cond-0` through `cond-99` |

The list of keys under test is `RENDERER_KEYS` (in `src/i18n.rs`) plus the hundred **condition
keys** derived from the code, `condition_key(Condition::from_u8(code))` for `code in 0..=99`. That
enumeration is what makes a provider adding a new WMO code safe: a code the catalog cannot name
fails the test. `cond-unknown` and the key constants are the only ways the code spells a key, so a
renderer cannot invent one at a call site.

## A missing key

A lookup that finds no message records `Note::MissingKey` once per key and returns the key itself,
so the output is honest instead of a half-rendered pattern. Missing keys are a bug in this crate,
not a user error: they are excluded from the warnings a normal run prints, and `-v` lists them after
the render, one line each:

```text
warning: no message for key `format-temp-c`
```

## No string is built by concatenation

A renderer never joins translated fragments into a sentence. Every user-visible string is one
Fluent message, and the parts a translator must reorder are **placeholders** inside it
(`$value`, `$weekday`, `$month`, `$day`, `$provider`, `$event`, `$time`, …). Dates are the clearest
case: `date-short` is `{ $weekday } { $day } { $month }` in English and largest-to-smallest in
Chinese, both driven by the catalog's own weekday and month names — the order is the translator's,
never `chrono`'s English. A message that needs an argument the call site forgot fails the
completeness test rather than printing `{$value}` in the middle of a table.
